# PipelineProbe Quickstart

A self-contained Docker Compose stack that runs a real PipelineProbe audit
against a small Airflow + dbt + Postgres setup. No accounts, cloud services, or
existing pipelines are needed: the warehouse data is generated locally when the
stack starts, and the dbt artifacts are checked-in fixtures.

## What runs

| Service | Role |
| --- | --- |
| `postgres` | Postgres 13. Holds the Airflow metadata database and a separate `warehouse` database seeded by `init-warehouse.sql`. |
| `airflow` | Apache Airflow 2.7.1 (standalone). Serves the UI on [http://localhost:8080](http://localhost:8080) and runs the eight demo DAGs from `dags/`. |
| `pipelineprobe` | One-shot container. Waits for Airflow, seeds a deterministic DAG run history, then audits the stack and writes the reports. |

The dbt project under `dbt_project/` is a recorded fixture: the audit reads
`dbt_project/target/manifest.json` and `run_results.json`, which describe two
models and their last run. No `dbt` command is executed by the stack.

## Run it

Prerequisites: Docker with Compose v2, a few GB of free disk (images plus the
seeded warehouse), and network access on the first run to pull images.

```bash
cd examples/quickstart
docker compose up --build
```

The `pipelineprobe` service waits for Airflow's health endpoint, seeds the demo
run history through the Airflow REST API, and runs `pipelineprobe audit`. When
it exits with code 0, the audit is finished. The Airflow service keeps running
so you can browse the UI; press `Ctrl+C` and run `docker compose down` when you
are done.

On systems with the legacy binary, `docker-compose up --build` works the same.

### Expected runtime

The first run takes several minutes on a typical laptop — roughly 5–10 minutes,
dominated by pulling the Airflow and Postgres images, building the
PipelineProbe image, and Airflow startup. Seeding the warehouse (just over 11
million synthetic rows) and the demo DAG runs adds about a minute. Later runs
with cached images are faster. Watch progress with:

```bash
docker compose logs -f pipelineprobe airflow
```

## Reports

When the audit completes, the generated reports are written into this
directory (they are not committed):

- `reports/pipelineprobe-report.html` — open in any browser
- `reports/report.json` — machine-readable issues and summary

The same summary is printed in the `pipelineprobe` service logs.

## Credentials

Airflow UI: <http://localhost:8080>, username `admin`, password `admin`.
These are demo credentials for the local stack only; do not reuse them
anywhere else.

## Findings this demo intentionally produces

The fixtures are sized and shaped so each audit category has something to
report. The exact health score is computed at run time; the report always
contains, qualitatively:

- **Airflow / tasks** — the two "unhealthy" DAGs (`daily_sales_pipeline` and
  `nightly_customer_sync`) have tasks with no retries (warnings) and no SLA
  (informational notes). The six `healthy_pipeline_*` DAGs have both, so the
  report is not uniformly bad.
- **Airflow / DAGs** — `nightly_customer_sync` fails two of its six seeded runs,
  which trips the high-failure-rate rule as a critical issue.
- **dbt** — `customers` has no tests (warning) and its last recorded run ended
  in `error` (critical). `orders` has two passing tests and succeeded, so it
  produces no dbt findings.
- **Warehouse** — `analytics.fact_orders` has just over 10 million rows
  (warning: very large table). `raw.stg_events` has just over 1.2 million rows
  and no `created_at` / `updated_at` columns (warning: missing audit
  timestamps).

Cost-insight rules stay quiet here: they need BigQuery or Snowflake billing
data, and this demo warehouse is Postgres.

## All data is synthetic

Every row in `analytics.fact_orders` and `raw.stg_events` is generated by
`init-warehouse.sql` when the database is first created. The DAG runs are seeded
through the Airflow API by `run-audit.sh`, and the dbt artifacts in
`dbt_project/target/` are hand-written fixtures recorded for this demo. All of
it is sample data for the bundled demo stack, not client or production data,
and nothing is sent anywhere except between the containers on the Compose
network.

## Reset and clean up

```bash
docker compose down       # stop the stack, keep the seeded volume
docker compose down -v    # stop and delete the database volume
```

With `-v`, the next `docker compose up` re-initialises Postgres and re-seeds the
warehouse.

## Troubleshooting

- If the `pipelineprobe` service times out waiting for Airflow, inspect
  `docker compose logs airflow airflow-init`; the eight demo DAGs must parse
  without import errors.
- If report files do not appear, check `docker compose logs pipelineprobe`; the
  container runs as an unprivileged user and needs write access to
  `examples/quickstart/reports/`.
- To re-run only the audit without recreating the stack:

  ```bash
  docker compose run --rm pipelineprobe
  ```
